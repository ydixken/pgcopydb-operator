# Prior Art & Design Inputs: pgcopydb-operator

## 1. Existing tools and their CRD domain models

### CloudNativePG (CNPG): Apache-2.0
The closest and richest prior art. Three relevant mechanisms:

- **`Cluster.spec.bootstrap.initdb.import`** ([docs](https://cloudnative-pg.io/docs/devel/database_import)): one-shot offline import at bootstrap using pg_dump/pg_restore run inside the init job of the new cluster (dumps land in a `dumps` folder on the PGDATA volume). Spec shape: `type: microservice|monolith`, `databases: []`, `roles: []` (monolith only), `source.externalCluster` (name reference), `pgDumpExtraOptions` / `pgRestoreExtraOptions` / stage-specific `pgRestorePredataOptions|DataOptions|PostdataOptions`, `postImportApplicationSQL`, `schemaOnly`. Microservice = single DB renamed to the destination app database; monolith = multiple DBs/roles preserved.
- **`externalClusters`** section: the canonical pattern for referencing a remote Postgres: `connectionParameters` (host, port, user, dbname, sslmode) + `password: {name, key}` (corev1 `SecretKeySelector`) + `sslCert`/`sslKey`/`sslRootCert` secret key selectors. Steal this wholesale for source/target connection modeling.
- **Declarative logical replication (v1.25+)**: standalone `Database`, `Publication`, `Subscription` CRDs ([docs](https://cloudnative-pg.io/docs/devel/logical_replication/), [issue #13](https://github.com/cloudnative-pg/cloudnative-pg/issues/13)). Explicitly marketed for online migrations from DBaaS and major-version upgrades, but it does not orchestrate cutover, sequence sync, or DDL; the user drives the sequence manually ([Gabriele Bartolini's CNPG Recipe 15](https://www.gabrielebartolini.it/articles/2024/12/cnpg-recipe-15-postgresql-major-online-upgrades-with-logical-replication/)). **Gap pgcopydb-operator fills: a single CR that owns the whole clone→follow→cutover lifecycle, target-agnostic (works against any Postgres, not just CNPG clusters).**

### Zalando postgres-operator: MIT
`postgresql` CRD has a `spec.clone` section: `{cluster, uid, timestamp}`: clone from a live cluster (pg_basebackup) or point-in-time from S3/WAL archive ([user docs](https://github.com/zalando/postgres-operator/blob/master/docs/user.md)). Also `spec.standby` (Patroni standby cluster: clone then keep streaming from WAL archive; conceptually "clone + follow" but physical, not logical). Lesson: modeling "source" as a small inline struct on the target resource works, but conflates cluster lifecycle with migration; a separate migration CRD is cleaner for our case.

### Percona Everest / everest-operator: Apache-2.0
Most directly analogous job-shaped design ([Data Importers overview](https://docs.percona.com/everest/backups_and_restore/dataimporters/overview.html), [blog](https://www.percona.com/blog/introduction-to-data-importers-in-percona-everest/), [everest-operator repo](https://github.com/percona/everest-operator)):
- **`DataImporter`** (cluster-scoped): reusable blueprint: container image with import logic, supported engines, required input config schema, engine-version constraints.
- **`DataImportJob`** (namespaced): a single execution: `spec.source` (location + credentials), `spec.target` (DatabaseCluster ref + connection details), importer-specific config. The operator materializes a Kubernetes Job running the importer container. This "CR → one owned Job → status mirrored back" pattern is exactly our shape.

### SchemaHero: Apache-2.0
Declarative schema management: `Database` CRD (connection + secret ref) and `Table`/`Migration` CRDs; operator computes ALTER drift and applies it ([repo](https://github.com/schemahero/schemahero)). Relevant only for the pattern of separating "connection object" (`Database`) from "work objects" (`Migration`); an option if we want a reusable `PostgresConnection`-style CRD instead of inlining source/target on every migration.

### DMS-style / migration operators
No true managed-DMS equivalent exists as a K8s operator. Adjacent: [quay/dba-operator](https://github.com/quay/dba-operator) (schema migration orchestration), [coderanger/migrations-operator](https://github.com/coderanger/migrations-operator), [Atlas Operator](https://atlasgo.io/blog/2023/07/03/versioned-migrations-kubernetes) (schema-only), [mariadb-operator](https://github.com/mariadb-operator/mariadb-operator) (cross-cluster replication for MariaDB). All schema-focused or engine-lifecycle-focused; none does bulk-copy + logical follow + cutover for Postgres.

### pgcopydb Kubernetes integrations
**None found.** Searches for "pgcopydb kubernetes operator" and "pgcopydb helm" return only generic Postgres operators and hand-rolled Job/Helm-hook migration patterns ([example](https://packagemain.tech/p/database-migrations-in-kubernetes)). Neon documents pgcopydb for migrations to their DBaaS ([Neon docs](https://neon.com/docs/import/pgcopydb)) but purely CLI. Greenfield space.

### pgcopydb itself: key facts for the design
- `pgcopydb clone --follow` = bulk copy + logical decoding replay; **cutover** is triggered by `pgcopydb stream sentinel set endpos --current` executed *in the same `--dir`* as the running clone (shared SQLite catalogs); i.e., the operator must exec into the running pod (or the container must poll an instruction channel) to trigger cutover ([follow ref](https://pgcopydb.readthedocs.io/en/latest/ref/pgcopydb_follow.html), [tutorial](https://pgcopydb.readthedocs.io/en/latest/tutorial.html)). Sequences sync after endpos is reached. DDL is not replicated (logical decoding restriction).
- **Progress**: `pgcopydb list progress --json` (and `--summary --json`) reads the SQLite catalogs in the work dir and reports tables/indexes planned/done/in-progress ([list ref](https://pgcopydb.readthedocs.io/en/latest/ref/pgcopydb_list.html)); `pgcopydb stream sentinel get --json` gives replay LSN / endpos state. Both are exec-able alongside the main process, the natural progress source for status updates.
- License: PostgreSQL license (permissive); upstream at [dimitri/pgcopydb](https://github.com/dimitri/pgcopydb) with Debian packages and a published container image.

## 2. CRD design for a job-like, long-running migration

References: [k8s API conventions](https://github.com/kubernetes/community/blob/main/contributors/devel/sig-architecture/api-conventions.md), [kpt CRD status convention](https://kpt.dev/reference/schema/crd-status-convention/).

- **Conditions over phase**: API conventions deprecate `phase` (state-machine enums break evolution). Use `status.conditions []metav1.Condition` via `meta.SetStatusCondition`. Rules: positive-polarity types only (`Ready=False`, never `NotReady`), CamelCase `reason` tokens, `lastTransitionTime` bumps only on status flips, always set `observedGeneration` (both top-level `status.observedGeneration` and per-condition). Pragmatic hybrid used by many operators (and fine per convention as long as conditions are authoritative): keep a human-friendly `status.phase` string *derived* from conditions for `kubectl get` printer columns, plus granular conditions like `CloneCompleted`, `Streaming`, `CutoverCompleted`, `Failed`. ([conditions-conventions writeup](https://oneuptime.com/blog/post/2026-02-09-crd-status-conditions-conventions/view), [RocketChat phases/conditions discussion](https://dev.to/rocketchat/conditions-phases-and-declarative-phase-rules-in-kubernetes-operators-l2h))
- **Spec immutability**: like `batch/v1 Job.spec.template`, migration source/target must be immutable after creation. Do it with CEL transition rules, no webhook: `+kubebuilder:validation:XValidation:rule="self == oldSelf",message="field is immutable"`; for optional-then-frozen fields combine `!has(oldSelf.x) || has(self.x)` with equality ([k8s blog: Enforce CRD Immutability with CEL](https://kubernetes.io/blog/2022/09/29/enforce-immutability-using-cel/), [kubebuilder CRD validation markers](https://book.kubebuilder.io/reference/markers/crd-validation.html)). Leave mutable only the intent knobs: `suspend`, `cutover` trigger, maybe resource sizing.
- **Idempotent reconcile of an external long-running process**: the reconciler must never re-run side effects based on its own memory: derive everything from (a) owned Job/Pod existence+status and (b) pgcopydb's own resumability (`--resume --not-consistent`, snapshot + sentinel in the work dir on a PVC). Terminal states (Succeeded/Failed after operator-level retries) become absorbing: reconcile observes and returns.
- **Suspend semantics**: mirror `Job.spec.suspend`: a `spec.suspend: bool` that deletes/scales-down the worker while preserving the work-dir PVC, and a `Suspended` condition. Note: suspending during logical-replication follow holds the replication slot open on the source (WAL retention risk); document it, surface it in status.
- **TTL/cleanup**: set `ttlSecondsAfterFinished` on owned Jobs, or rely on ownerReferences + a `spec.ttlSecondsAfterFinished`-style field on the migration CR itself; K8s [TTL-after-finished controller](https://kubernetes.io/docs/concepts/workloads/controllers/ttlafterfinished/) deletes cascadingly and honors finalizers. Beware: unmanaged Jobs default to orphaning pods on delete; always delete with foreground/background cascading, never orphan.

## 3. Running the per-CR workload

- **Job vs bare Pod**: mainstream pattern (Everest DataImportJob, CNPG init jobs) is a **Job with `backoffLimit: 0`** and operator-driven retries: each attempt is a fresh Job (or the operator recreates it), so retry policy, backoff and attempt-counting live in the CR status where users can see them, rather than in opaque Job-controller retries. Job gives free semantics: completion tracking, `ttlSecondsAfterFinished`, `suspend`, `activeDeadlineSeconds`. A bare Pod buys nothing except losing those. Caveat for us: the follow phase is indefinite-duration, which is un-Job-like, but a never-completing Job with backoffLimit 0 works fine; the operator decides completion by observing pgcopydb exit.
- **Single container, sidecar-free** is the norm for this kind of runner; pgcopydb is a single binary that forks its own subprocesses. A thin entrypoint wrapper (ours) around `pgcopydb clone --follow` handles signal forwarding and structured logging.
- **Config passing**: connection strings/passwords via env from `secretKeyRef` or a mounted Secret volume. Mounted-file is slightly preferable for passwords (`PGPASSFILE` / `.pgpass`, avoids env leakage in `kubectl describe` and crash dumps); non-secret options can be flags/env rendered by the operator. Never bake URIs with passwords into the pod spec.
- **Cancellation**: delete the owned Job with **foreground cascading deletion** (propagationPolicy=Foreground) so pods (and the pgcopydb process, via SIGTERM + terminationGracePeriod) are gone before the CR finalizer proceeds to drop the replication slot / sentinel on the source. The operator's finalizer must also clean the source-side replication slot pgcopydb created, the single most important cleanup, since a leaked slot bloats source WAL.
- **Progress reporting options** (in practice a combination):
  1. **Operator exec-polls** `pgcopydb list progress --json` / `pgcopydb stream sentinel get --json` in the worker pod on a requeue interval and writes results into `status`: simplest, uses pgcopydb's own catalogs, no protocol to invent. Needs `pods/exec` RBAC.
  2. Wrapper process in the container runs the same loop and **PATCHes the CR status itself** (needs a scoped ServiceAccount with status-patch RBAC); pushes instead of polls, but grants API access to the workload.
  3. Log parsing: fragile, avoid as the primary channel.
  Cutover has the same shape in reverse: either operator exec-runs `pgcopydb stream sentinel set endpos --current`, or the wrapper polls a "cutover requested" signal (annotation/spec field via downward API is not enough since it needs live updates; an exec from the operator is the pragmatic choice).

## 4. Cross-cluster access

- Model each side as a connection struct à la CNPG `externalClusters`: `{host, port, dbname, user, sslMode, passwordSecretRef: {name, key}, sslCertSecretRef, sslKeySecretRef, sslRootCertSecretRef}` using `corev1.SecretKeySelector` (`{name, key}`), the ecosystem-standard shape (CNPG, SchemaHero, mariadb-operator all follow it). Alternatively/additionally accept a full-URI secret ref (`uriSecretRef`) for DBaaS sources like RDS/Neon where users already hold a DSN.
- External reachability is the user's problem (LoadBalancer, ExternalName Service, VPN); the operator only needs routable host + `sslmode` (`require`/`verify-full` with mounted root cert). Mount TLS secrets as volumes into the worker pod with 0600 perms (libpq requires restrictive key perms).
- No kubeconfig access to the remote cluster is needed: everything is plain Postgres wire protocol, which is a feature: source can be RDS, on-prem, another cluster's CNPG behind a LB.

## 5. Helm packaging norms (2026)

- **CRDs**: Helm's official stance keeps CRDs in `crds/` (installed first, never templated, never upgraded, never deleted) ([Helm best practices](https://helm.sh/docs/chart_best_practices/custom_resource_definitions/)). Because Helm won't upgrade `crds/`, most operator charts in practice (Argo, cert-manager discussion [#6179](https://github.com/cert-manager/cert-manager/issues/6179)) moved CRDs to `templates/` gated by `crds.install`/`crds.keep` values and annotated `helm.sh/resource-policy: keep` so uninstall doesn't nuke CRs. For a young operator with evolving CRDs, the templates+keep-annotation approach is the pragmatic 2026 default.
- **Webhooks**: avoid entirely at v1. Use CEL `x-kubernetes-validations` (via kubebuilder XValidation markers) for validation + immutability, and defaulting via `+kubebuilder:default`. This removes the cert-manager dependency and the whole CA-injection dance that plagues operator charts ([VAP/CEL rationale](https://www.systemshardening.com/articles/kubernetes/validating-admission-policy-cel/)). If webhooks become unavoidable later (conversion for multi-version), the fallback patterns are cert-manager-optional + helm-generated self-signed certs (kube-prometheus-stack style).
- **values.yaml conventions**: `image.{repository,tag,pullPolicy}`, `imagePullSecrets`, `rbac.create`, `serviceAccount.{create,name}`, `resources`, `nodeSelector/tolerations/affinity`, `watchNamespaces` (empty = cluster-wide; drives Role vs ClusterRole rendering), `metrics.serviceMonitor.enabled`, plus operand defaults (`worker.image`, `worker.resources`).
- **Publishing**: OCI is the norm: `helm push` to `oci://ghcr.io/<org>/charts` alongside the container images (Helm ≥3.8 native, [GHCR guide](https://niklasmtj.de/blog/use-ghcr-to-host-helm-charts/)); list on Artifact Hub via OCI repo registration + `artifacthub-repo.yml` pushed with oras ([Artifact Hub docs](https://artifacthub.io/docs/topics/repositories/helm-charts/)). gh-pages index.yaml is legacy.

## 6. Kubebuilder in 2026

- Current line: **kubebuilder v4.x** (v4.12.0 in Feb 2026 and later releases; [releases](https://github.com/kubernetes-sigs/kubebuilder/releases)) with the **go/v4 plugin**; recent releases track **controller-runtime v0.24.x**, controller-tools v0.21, Go 1.26, Kubernetes 1.36 deps. envtest version is now pinned in scaffolded projects (controller-runtime ≥0.24).
- v4.12+ adds `--namespaced` and `--multigroup` init flags, and a **helm/v2-alpha plugin** that scaffolds a Helm chart from the kustomize config; worth evaluating as chart starting point, then hand-maintain.
- Scaffolded tests use **Ginkgo v2 + Gomega + envtest** by default; plain `go test` with envtest is entirely viable (envtest "should work with any testing setup" per [its docs](https://pkg.go.dev/sigs.k8s.io/controller-runtime/pkg/envtest)); dropping Ginkgo just means rewriting the generated suite bootstrap.
- Multi-version CRDs: supported (kubebuilder multiversion tutorial), but conversion between versions requires a conversion webhook, a strong argument to stay on a single `v1alpha1` (or jump carefully to `v1beta1`) until the API stabilizes, keeping the no-webhook stance.

## Synthesis: what to steal
- **CNPG**: `externalClusters`-style connection struct with `SecretKeySelector` password + SSL cert refs; `microservice/monolith`-like scoping vocabulary (databases/roles filtering); Apache-2.0 code to read for exec-into-pod plumbing.
- **Everest**: two-CRD split idea (blueprint vs execution); probably overkill for v1; a single `PgCopyMigration`-style namespaced CRD owning one Job is enough, but keep the Everest shape in mind for pluggable importers.
- **Job pattern**: owned Job, `backoffLimit: 0`, operator-counted retries in status, `ttlSecondsAfterFinished`, foreground cascading delete, finalizer that drops the source replication slot.
- **Status**: `metav1.Condition` array (positive polarity, observedGeneration) + derived printer-column phase; progress numbers from exec'd `pgcopydb list progress --json`.
- **Cutover**: mutable `spec` trigger (e.g. `spec.cutover.mode: Manual|Automatic` + a user action) that the operator translates into an exec of `pgcopydb stream sentinel set endpos --current` in the worker pod.
- **Packaging**: templated CRDs with `helm.sh/resource-policy: keep`, no webhooks (CEL validation), OCI chart on ghcr + Artifact Hub.

## Open questions from this research pass

- Whether an official/maintained pgcopydb container image exists at a stable registry path (ghcr.io/dimitri/pgcopydb vs Docker Hub) and its tagging/version cadence; not verified in this pass; also current pgcopydb release number (docs show 0.17/0.18~dev branches).
- Percona Everest operator license was not explicitly confirmed (repo suggests Apache-2.0; note the openeverest fork exists; governance/fork situation worth a closer look before copying patterns).
- Exact latest kubebuilder version as of Aug 2026 (>= v4.12.0, controller-runtime v0.24.x); pin precisely at scaffold time.
- Whether pgcopydb's sentinel table/commands work cleanly when the operator execs them in a separate process namespace within the same container vs a shared-PVC second container (docs only require same --dir; not tested).
- How pgcopydb handles SIGTERM mid-clone with respect to --resume safety (resumability documented, but graceful-shutdown behavior on signal should be verified empirically).
- Whether kubebuilder's helm/v2-alpha plugin output is production-usable or better treated as a one-time scaffold.
