# Competitive comparison

An engineering review of pgcopydb-operator against the open-source Kubernetes operators closest to its problem space, written 2026-08-08 for the M5 W-H workstream. It compares design decisions with evidence from upstream code and docs, and ends in an adopt/reject list. It is not marketing; where a compared project does something better, that is stated and, where sensible, adopted.

Projects reviewed, at their state on 2026-08-08:

- [CloudNativePG](https://github.com/cloudnative-pg/cloudnative-pg) (CNPG): Postgres cluster operator with import machinery and declarative logical replication. Docs cited from the current [docs site](https://cloudnative-pg.io/docs/devel/) (now Docusaurus; the old `documentation/current` paths only redirect).
- [OpenEverest](https://github.com/openeverest/openeverest-operator) (until January 2026: Percona Everest; the repos and docs moved with the [rebrand](https://www.percona.com/blog/blog-post-good-bye-percona-everest-hello-openeverest/)): multi-engine DBaaS platform with a pluggable backup-import framework.
- [Zalando postgres-operator](https://github.com/zalando/postgres-operator): the oldest widely used Postgres operator, with clone and standby bootstrap features. Actively maintained; v2.0.0 shipped 2026-07-27.
- [mariadb-operator](https://github.com/mariadb-operator/mariadb-operator): not Postgres, but the closest study in Job orchestration and condition conventions for dump/restore-shaped work.
- [SchemaHero](https://github.com/schemahero/schemahero): included to draw a boundary, not as a competitor. Its `Migration` kind is a generated DDL plan awaiting approval (schema management); it moves no data.

One claim needs stating carefully: we are not aware of any other Kubernetes operator that wraps pgcopydb. GitHub name, description, topic, and README searches plus ArtifactHub turn up no operator and no chart; the closest match is [abhixops/pgcopydb](https://github.com/abhixops/pgcopydb), a plain Deployment YAML plus Dockerfile. Real-world pgcopydb use on Kubernetes today looks like Meltwater's 2026 migration write-up: a [hand-built short-lived pod](https://underthehood.meltwater.com/blog/2026/03/19/migrating-a-1tb-postgresql-from-aws-to-azure-with-pgcopydb/) with Secrets and ConfigMaps, "rather than custom operators". PlanetScale [documents pgcopydb as its Postgres import path](https://planetscale.com/docs/postgres/imports/postgres-migrate-pgcopydb) and maintains a fork, run on dedicated VMs, not Kubernetes. That is the gap this operator fills.

Adjacent tools that keep coming up but are out of scope here: [pg_easy_replicate](https://github.com/shayonj/pg_easy_replicate) (a CLI that orchestrates logical replication and switchover; the closest functional analogue to our cutover, with no Kubernetes API), [pgstream](https://github.com/xataio/pgstream) (replication with DDL support, no operator), [Debezium](https://github.com/debezium/debezium), which does ship an [operator with a `DebeziumServer` CRD](https://debezium.io/documentation/reference/stable/operations/debezium-operator.html) but streams change events to a broker with no bulk load and no cutover concept, and [PeerDB](https://github.com/PeerDB-io/peerdb) (AGPL-3.0, Postgres to warehouses).

## 1. CRD ergonomics

**Spec shape.** Our surface is one namespaced kind, [`Migration`](https://github.com/ydixken/pgcopydb-operator/blob/main/api/v1alpha1/migration_types.go), owning the whole lifecycle: clone options, follow, cutover, verification, work volume, runner, retry budget. Every compared project splits migration-adjacent behavior across resources or buries it in a larger object. CNPG models import as a bootstrap property of a `Cluster` ([`spec.bootstrap.initdb.import`](https://cloudnative-pg.io/docs/devel/database_import)) and online migration as an assembly of four resources (source `Publication`, schema-only import, `Subscription`, plus a manual sequence sync, see section 6). Zalando's [`spec.clone` and `spec.standby`](https://postgres-operator.readthedocs.io/en/latest/user/) are bootstrap-time properties that "do not affect the already running cluster". OpenEverest's import is a field on a new `DatabaseCluster` (`spec.dataSource.dataImport`), immutable after creation, executed once.

**Defaulting and validation.** We use CEL exclusively: `+kubebuilder:default` markers, enums, and `XValidation` rules covering the connection one-of (`uriSecretRef` XOR inline fields), three pgcopydb filter exclusion rules, source/target/follow immutability (`self == oldSelf` transition rules), the slot-name charset (load-bearing: the name is interpolated into SQL), and plugin-dependent field gating (`wal2jsonNumericAsString` requires `plugin: wal2json`). No webhooks, so no serving certificates, no failure-policy trade-off, and validation cannot be switched off per-object. The compared field:

- CNPG runs mutating and validating [admission webhooks](https://cloudnative-pg.io/docs/devel/security) on port 9443 with operator-provisioned certificates (cert-manager not required). Its own security docs are candid that webhook validation is advisory, since an actor who can write the resource can also disable the webhook. We found no CEL rules in its CRDs.
- mariadb-operator uses all three mechanisms at once: validating webhooks (immutability enforced via `webhook:"inmutable"` struct tags, [backup_webhook.go](https://github.com/mariadb-operator/mariadb-operator/blob/main/internal/webhook/v1alpha1/backup_webhook.go)), CEL for cross-field rules (the Galera odd-replica-count rule in [mariadb_types.go](https://github.com/mariadb-operator/mariadb-operator/blob/main/api/v1alpha1/mariadb_types.go)), and Go-side `Validate()`/`SetDefaults()`. The webhook path needs a built-in cert-controller the docs describe as "a minimal cert-manager".
- Zalando ships no webhooks at all; validation is the structural schema plus reconcile-time failure, surfacing as an opaque status string. A typo'd field is pruned silently.
- OpenEverest validates importer parameters against a JSON schema embedded in the `DataImporter` CR ([`config.openAPIV3Schema`](https://github.com/openeverest/openeverest-operator/blob/main/api/everest/v1alpha1/dataimporter_types.go)), but at reconcile time in the controller, not at admission, so a bad config becomes a reconcile error instead of a rejected apply.

Our conclusion stands confirmed rather than challenged: everything we need is expressible in CEL, and the operators that chose webhooks paid for them in certificate plumbing (mariadb-operator) or honesty about their advisory nature (CNPG). The decision log entry of 2026-08-07 ("CEL validation + defaults, no admission webhooks in v1") survives contact with the field.

**Secret handling.** Our connections reference Secrets (`passwordSecretRef`, `uriSecretRef`, TLS material); passwords are projected as files and assembled into a libpq passfile at container start, so credentials appear in neither argv, nor the Job spec, nor CR status ([internal/conn](https://github.com/ydixken/pgcopydb-operator/blob/main/internal/conn/conn.go)). CNPG similarly references password Secrets from `externalClusters`. Zalando's clone-from-S3 path takes `s3_access_key_id` and `s3_secret_access_key` as plain strings in the manifest ([cluster_manifest.md](https://github.com/zalando/postgres-operator/blob/master/docs/reference/cluster_manifest.md)); an issue asking for [secret references](https://github.com/zalando/postgres-operator/issues/2363) is open. OpenEverest mounts a Secret holding a `request.json` with source and target credentials into the import Job. None of the compared projects does anything we should copy here.

**Immutability.** Ours is CEL transition rules on `source`, `target`, and `follow`, admission-enforced. mariadb-operator enforces immutability in webhooks. CNPG marks `cluster.name` immutable on its `Database`/`Publication`/`Subscription` kinds. Zalando has none (spec is freely mutable; the reconciler copes). OpenEverest marks `dataSource.dataImport` immutable via the same CEL idiom we use.

## 2. Status and conditions

Ours: `status.conditions` is `[]metav1.Condition` written through `meta.SetStatusCondition`, every condition carrying `observedGeneration`, positive-polarity types (`Validated`, `CloneCompleted`, `Streaming`, `CaughtUp`, `CutoverCompleted`, `Verified`, `Complete`, `Failed`), stable reasons (`PreflightFailed`, `BackoffLimitExceeded`, `DrainIncomplete`, `SchemaMismatch`, ...), plus a `status.observedGeneration`, a derived `phase` enum for the printer column, and terminal-state absorption. Conditions are authoritative; the phase is documented as a summary ([migration_types.go](https://github.com/ydixken/pgcopydb-operator/blob/main/api/v1alpha1/migration_types.go), [live-migration guide](../operations/live-migration.md)).

What the field does:

- CNPG's `Cluster` uses `metav1.Condition` (`Ready`, `ContinuousArchiving`, `LastBackupSucceeded`) but its phase strings are full English sentences: `"Cluster in healthy state"`, `"Waiting for user action"` ([cluster_types.go](https://github.com/cloudnative-pg/cloudnative-pg/blob/main/api/v1/cluster_types.go)). Sentences read well in `kubectl get` and are unusable in field selectors, metric labels, or GitOps health rules, which pushes all automation to the `Ready` condition. Its newer CRDs (`Database`, `Publication`, `Subscription`) drop conditions entirely for a flat `applied *bool` + `message` + `observedGeneration` triple ([database_types.go](https://github.com/cloudnative-pg/cloudnative-pg/blob/main/api/v1/database_types.go)). So the same project ships both conventions; our conditions-everywhere approach is a defensible position between them.
- mariadb-operator uses conditions with a surprise: `Complete` means terminal, not successful. A failed backup Job sets `Complete: True` with reason `JobFailed` and message `"Failed"` ([complete.go](https://github.com/mariadb-operator/mariadb-operator/blob/main/pkg/condition/complete.go)), so `kubectl get backup` shows `COMPLETE=True` for a failure and consumers must branch on the reason. Its conditions also never set `observedGeneration` ([condition.go](https://github.com/mariadb-operator/mariadb-operator/blob/main/pkg/condition/condition.go)), so staleness is undetectable. Our separate `Complete`/`Failed` types with honest polarity, and per-condition generations, avoid both traps.
- Zalando's status is one string with eight values (`Creating`, `Running`, `SyncFailed`, ...) and an `Error` field tagged `json:"-"` that never reaches the API ([postgresql_type.go](https://github.com/zalando/postgres-operator/blob/master/pkg/apis/acid.zalan.do/v1/postgresql_type.go)). Users report [`Running` shown while pods are stuck Pending](https://github.com/zalando/postgres-operator/issues/2864) and had to write [custom Argo CD health checks](https://github.com/zalando/postgres-operator/issues/1693) because there is nothing structured to read. Zalando's own [PR #3005](https://github.com/zalando/postgres-operator/pull/3005) acknowledges the flat status as a gap. This is the cautionary tale our conditions-first design was built against.
- OpenEverest's `DataImportJob` status is a bare string `state` (constants `Pending`/`Running`/`Succeeded`/`Failed`/`Error`, no enum in the schema) plus `message`; no conditions ([dataimportjob_types.go](https://github.com/openeverest/openeverest-operator/blob/main/api/everest/v1alpha1/dataimportjob_types.go)).

Where they beat us: printer columns. mariadb-operator's CRDs print the leading condition's status and its message (`kubectl get restore` shows `COMPLETE` and a human `STATUS` column read from `.status.conditions[?(@.type=="Complete")].message`), and CNPG's `Cluster` prints instance counts and the primary. Our columns are `Phase`, `Tables`, `Attempts`, `Age`, and `Tables` is currently always empty because pgcopydb 0.18's `list progress` is broken upstream ([#1036](https://github.com/dimitri/pgcopydb/issues/1036), see the [ledger](https://github.com/ydixken/pgcopydb-operator/blob/main/MILESTONES.md)). Adopt item 1 fixes the columns.

## 3. Day-2 operations

What we have, from the [operations pages](../operations/live-migration.md) and controller: suspend/resume that deletes the worker with foreground propagation (clean SIGTERM) while keeping the work PVC, with a `SlotRetained` warning event on live migrations; operator-owned retries (`backoffLimit` on the CR, each attempt a fresh Job resuming from pgcopydb's catalogs, attempt count and failure reason in status); a preflight Job that fails follow migrations before any data moves, with the exact `GRANT` to run in the condition message; a drain-verify gate that refuses to trust the worker's exit code at cutover; a cleanup Job behind a finalizer, with an escape hatch (`CleanupFailed` warns and releases deletion when the source is gone); `ttlSecondsAfterFinished`; eight Prometheus gauges; and a troubleshooting table built from failures found live.

The comparison, honestly:

- Nobody else in this set has a cutover primitive. CNPG's online flow ends with the user cutting over by hand after a manual `kubectl cnpg subscription sync-sequences` ([logical_replication](https://cloudnative-pg.io/docs/devel/logical_replication)). Zalando's documented standby promotion is `kubectl exec` into the leader and `patronictl edit-config` ([user guide](https://postgres-operator.readthedocs.io/en/latest/user/)). OpenEverest's near-zero-downtime story is a [manual psql runbook](https://openeverest.io/documentation/1.12.0/reference/postgresql12_migration.html). mariadb-operator's migration story is dump, upload to S3, `bootstrapFrom`, and you handle the switch ([logical_backup.md](https://github.com/mariadb-operator/mariadb-operator/blob/main/docs/logical_backup.md)).
- Retries: mariadb-operator exposes `backoffLimit` (default 5) but passes it to the Job, so attempt history lives in Job internals. Our operator-counted attempts exist precisely so `status.attempts` and per-attempt failure reasons survive on the CR. Nothing to adopt; the designs differ deliberately.
- Suspend: mariadb-operator's `spec.suspend` pauses the entire reconciliation loop for maintenance ([suspend.md](https://github.com/mariadb-operator/mariadb-operator/blob/main/docs/suspend.md)); its docs are explicit that everything stops. Ours stops the workload but keeps the controller watching, which is what lets it warn about WAL retention while suspended. Different tools for different jobs; ours is the right one for a migration (see reject list).
- Observability gaps on our side, named: `status.progress` and the tables/bytes gauges are dark until upstream fixes pgcopydb `list progress` (tracked in [MILESTONES.md](https://github.com/ydixken/pgcopydb-operator/blob/main/MILESTONES.md)); deterministic failures (bad credentials) still burn the retry budget one attempt at a time (open ledger item); and GitOps tools have no built-in understanding of our conditions, the same problem Zalando users hit. Adopt item 3 addresses the last one with documentation, which is all it needs.

## 4. Documentation

CNPG sets the bar: roughly sixty task-focused pages on a versioned Docusaurus site, an auto-generated API reference built with elastic/crd-ref-docs (the same tool we already use for [our API reference](../reference/api.md)), and dedicated failure-modes and troubleshooting pages. Its site's [move to Docusaurus](https://cloudnative-pg.io/docs/devel/) broke every old `documentation/current` deep link, a reminder to keep our site URLs stable. Zalando's ten readthedocs pages put clone and standby as subsections of one long user guide, and users file issues asking [where cloning is documented](https://github.com/zalando/postgres-operator/issues/858). mariadb-operator keeps about thirty task-grouped markdown pages in-repo, which works well at its scale. OpenEverest's import docs are four short pages, with the custom-importer contract documented only in a [repo markdown file](https://github.com/openeverest/openeverest-operator/blob/main/docs/guides/build_your_own_dataimporter.md).

Ours today is the mkdocs-material site the W-G workstream just landed: quickstart, installation, configuration, the [live-migration runbook](../operations/live-migration.md), lifecycle, and a [troubleshooting table](../troubleshooting.md) with causes and fixes drawn from live failures, [the prerequisites reference](../reference/prerequisites.md) with the exact grants, the generated [API reference](../reference/api.md), an [option-coverage audit](../reference/coverage.md), and commented [examples](https://github.com/ydixken/pgcopydb-operator/tree/main/docs/examples). The strict build and API-staleness gate land us structurally where mariadb-operator is and closes most of the distance to CNPG at our (much smaller) API size. What the site does not yet include and CNPG has: a conditions/reasons reference (adopt item 4) and an integration recipe for the dominant Postgres operator (adopt item 2).

## 5. Testing signals

CNPG runs a per-commit e2e matrix on kind across Kubernetes 1.31 through 1.35 and PostgreSQL 14 through 18 (the [version files](https://github.com/cloudnative-pg/cloudnative-pg/blob/main/.github/kind_versions.json) already carry 1.36 and PG 19 beta), with depth tiers per trigger, optional cloud engines, and, at the deepest tier, a second "-prime" operator build to exercise rolling operator upgrades mid-suite ([e2e docs](https://cloudnative-pg.io/docs/devel/e2e), [continuous-delivery.yml](https://github.com/cloudnative-pg/cloudnative-pg/blob/main/.github/workflows/continuous-delivery.yml)). Its resilience coverage is failure-injection style (operator pod deletion and eviction, corrupted PVC, failover timing bounds), not a chaos harness.

Ours: an envtest unit suite (coverage around 53%, W-B raises it to 75% or better) and a ten-scenario Ginkgo e2e suite that runs against a real cluster with real storage and live CNPG source/target clusters, local-only by decision ([test/e2e](https://github.com/ydixken/pgcopydb-operator/blob/main/test/e2e/e2e_test.go), timings and invariants in the [ledger](https://github.com/ydixken/pgcopydb-operator/blob/main/MILESTONES.md)). Real-cluster e2e catches what kind cannot (storage behavior, live CNPG defaults like the 5s `wal_sender_timeout` that killed early follow runs), at the cost of not running per-commit.

Deltas, and where M5 already covers them: no PG version matrix (W-E adds 14 to 18 combinations), no chaos suite (W-D adds pod kills mid-clone, disk-full, concurrent migrations, cutover interruption; per the research above, that is a genuine differentiator, since none of the compared projects has a chaos harness either), no large-data tiers (W-C adds ~12GB default and ~120GB stress). Two things CNPG has that no current workstream covers: a Kubernetes version matrix and an operator-upgrade e2e. The first is expensive and low-yield for an operator whose API surface is one CRD and some Jobs; the second is cheap, real (W-F introduces a second API version), and worth adopting (item 5).

## 6. Scope honesty and the CNPG seam

What this operator deliberately does not do: provision Postgres, manage HA, take backups, or perform in-place upgrades. The [design spec](../superpowers/specs/2026-08-07-operator-design.md) lists the non-goals; the reviewed field validates the boundary. Every compared operator that owns clusters treats data movement as a bootstrap detail of the cluster object, and it shows: no resumability, no phases, no cutover, minimal status. Owning the migration as its own resource with its own lifecycle is the one design decision none of them made, and it is the entire product.

The flip side is also true and worth stating plainly: for a CNPG-to-CNPG move where the source is healthy and small, CNPG's own import (`initdb.import`, one manifest, no extra operator) is simpler, and its `Publication`/`Subscription` kinds cover the online case for users who are comfortable assembling the pieces and cutting over by hand. Our value begins where those stop: sources anywhere libpq reaches (DBaaS, VMs, other operators), parallel bulk copy (CNPG's import is single-stream `pg_dump`/`pg_restore`; CNPG issue [#6874](https://github.com/cloudnative-pg/cloudnative-pg/issues/6874) asks for exactly the parallelism pgcopydb has), resumable attempts, preflighted prerequisites, a supervised cutover with a drain proof, and verification.

That makes CNPG a seam, not a rival. Migrating into a CNPG cluster is already our best-tested path: the e2e fixtures are CNPG `Cluster` resources, [the prerequisites reference](../reference/prerequisites.md) documents the CNPG `managed.roles` route for the `REPLICATION` attribute, and the [troubleshooting table](../troubleshooting.md) carries the CNPG `wal_sender_timeout` fix. What is missing is a page that says so end to end (adopt item 2).

## Adopt

Each item: what, from whom, why, effort (S/M/L). Items marked "this push" are pure docs or trivially safe code and are fully specified here; none are implemented in this review.

1. **Condition-aware printer columns** (from mariadb-operator; effort S; this push). Replace the dead `Tables` column and surface outcome and lag: on [`Migration`](https://github.com/ydixken/pgcopydb-operator/blob/main/api/v1alpha1/migration_types.go), change the printcolumn markers to `Phase` (keep), `Complete` from `.status.conditions[?(@.type=="Complete")].status`, `Lag` from `.status.replication.lagBytes` (priority 1), `Attempts` (keep), `Age` (keep), dropping `Tables` until pgcopydb #1036 is fixed upstream. Then `make manifests` and copy the regenerated CRD into the chart. Rationale: the two questions an operator asks at a glance are "is it done" and "how far behind is the stream", and today's columns answer neither.
2. **"Migrating into a CloudNativePG cluster" recipe** (from CNPG's task-page docs style; effort S; this push). One docs page (or usage-guide section, W-G will place it): target host is the `-rw` Service, reuse of the CNPG app Secret, the non-superuser target grant block from PREREQUISITES.md, `managed.roles` with `replication: true` for CNPG sources, raising `wal_sender_timeout` via `spec.postgresql.parameters`, and a closing note that the e2e suite runs exactly this shape. Rationale: it is our best-proven path and the most likely first contact for CNPG users, whose native import CNPG's own issue tracker calls slow for large databases (#6874).
3. **Argo CD health check snippet** (lesson from Zalando issues #1693/#2864; effort S; this push). A documented `resource.customizations` Lua snippet mapping our conditions to GitOps health: `Failed=True` to Degraded, `Complete=True` to Healthy, `Suspended` phase to Suspended, anything else Progressing with the phase in the message. Pure docs; GitOps users otherwise each rediscover this.
4. **Conditions and reasons reference** (from CNPG's API-reference completeness; effort S; this push). A table listing all eight condition types, their polarity, and every reason string the controller sets (`PreflightFailed`, `DrainIncomplete`, `SlotRetained` event reason, `SchemaMismatch`, ...), with one line on when each appears. Reasons are API contract; today they are discoverable only in code and prose. Feeds the W-G reference section.
5. **Operator-upgrade e2e spec** (from CNPG's "-prime" upgrade tier; effort M). One scenario: install the latest released chart, start a follow migration with live writes, upgrade the operator to the local build mid-stream, assert the migration completes and conditions survive. Becomes real the moment W-F serves two API versions.

## Reject

Each item: what, why not, and when to revisit.

1. **Admission webhooks** (CNPG, mariadb-operator). CEL already enforces every rule we have at admission time, with no certificate infrastructure; CNPG's own docs concede webhook validation is advisory. Revisit when a second served API version needs a conversion webhook (after W-F), and only then.
2. **Decomposing the API into multiple kinds** (CNPG `Database`/`Publication`/`Subscription` granularity). The single kind owning clone-through-cutover is the product; CNPG's four-resource flow plus manual steps is the gap we exist to close. Revisit if users need slots or publications managed independently of a migration; the connection struct is already a named type for that future.
3. **A pluggable importer framework** (OpenEverest `DataImporter`). Genuinely good design for a multi-engine platform, and credit where due: the JSON-schema-described parameters are elegant. But we wrap exactly one tool, and a plugin seam with one plugin is dead weight. Revisit only if a second migration engine becomes a real requirement.
4. **Free-text phases** (CNPG). Sentences in `status.phase` read nicely and automate terribly. Our enum plus authoritative conditions serves both audiences. Not planned for revisit.
5. **Reconciliation-wide suspend** (mariadb-operator). A total pause would also stop the slot-retention warning and finalizer safety while WAL piles up on the source, which is the one thing a suspended live migration must keep saying. Our workload-level suspend is the right scope. Revisit if a maintenance case appears that workload suspend cannot serve.
6. **A kubectl plugin** (CNPG's `kubectl cnpg`). At one CRD with a one-screen status, `kubectl get pgm` and conditions cover it; a plugin would be surface without depth. Revisit if status outgrows a screen or cutover approval wants a friendlier verb.
7. **Provisioning, HA, backups, in-place upgrades** (Zalando, CNPG, mariadb-operator scope). Deliberate non-goals per the design spec; a migration is this operator's answer to a major upgrade, and integration recipes beat reimplementation. Not planned for revisit as in-tree features.
